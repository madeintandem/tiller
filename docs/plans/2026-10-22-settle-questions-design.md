# Settle questions before approve

Designed and settled 2026-10-21 to 2026-10-22 from issue #152, item 1. Built 2026-10-22 on branch settle-questions. It ships in the same release as gate reuse (`docs/plans/2026-10-21-gate-reuse-design.md`, item 4) and the specify batch (`docs/plans/2026-10-21-specify-guidance-design.md`, items 2, 3, and 6).

## Problem

On KoPanda, 146 owner questions blocked work for 27.7 hours. Many came from Done-when criteria that contradicted each other or the code, found only once building started. One feature, series-and-authors, spent 339 of its 529 minutes waiting on the owner.

Three things in Tiller let that happen:

- **`approve feature` ignores open questions.** `start`, `check`, and `submit` refuse while an open question names the node or an ancestor (`guardFeature` and `guardTask`, `internal/core/mutate/transition.go`), but the plan gate does not. A plan approves with a question open, then every task under it waits at `start`.
- **Specify never records a question.** It writes open facts for execution to determine (#140), and its readout says "Questions and commentary are yours to add freely", which means chat. A question asked only in chat is invisible to every gate and every later session.
- **Execute stops on every finding past a departure.** A wrong fact in `task.md` is built through and noted, but a finding that changes the feature's behavior, a criterion, the task's scope, or a dependency is "stop and route that change" (`internal/skills/execute/SKILL.md`, the departure paragraph). Each finding is its own full stop, with the owner absent.

Routing can already build around a held task: a task held by an open question is skipped and the next legal task runs, with an Order note naming the blocker. That only helps when the question is recorded and names the narrowest node.

## What this is

Questions get found and answered while the human is at the plan gate, and the ones that only surface mid-run are recorded, built around, and asked together.

It refuses to judge prose. The CLI never checks that an answer reached the plan; the human reviews that in the diff, as with every other plan prose (AGENTS.md, principle 1).

It refuses to add an escape. A plan with an open question does not approve. The human answers, even provisionally, or specify narrows or drops the question.

It refuses to stop a run for a question alone. Execute stops when the run has no legal work left or at a stop it already makes.

## Decisions settled

1. **`approve feature` refuses while an open question blocks the plan.** An open question naming the feature, its epic, or any of its live tasks refuses the specced-to-ready approve, naming each question and the `tiller answer question` remedy. The human is reliably present at approve; answering there costs minutes, answering mid-run cost KoPanda 27.7 hours. A warning was rejected: the console approves without the readout in view, so a warning repeats today's failure whenever nobody reads it.
2. **Specify ends with a final pass that sorts every finding three ways.** After the plan is written and before `spec feature`, specify reads the whole plan against itself and the code: criteria against each other, criteria against `feature.md`, each `task.md` against the code it names, and the task plans against each other. Each finding is (a) settled by reading, so the prose is fixed and nothing is recorded; (b) settleable only by code written later, so it is an open fact (#140); or (c) a decision only the human can make (product behavior, acceptance, scope), so it is recorded with `tiller add question "<statement>" --title "<short>" --blocks <node>`, where `--blocks` names the narrowest node the answer could change: the one task if only its plan depends on it, the feature only when a criterion does. A chat-only question is no longer allowed, because the gate cannot see it. The narrow pin matters more under decision 1, since a question pinned to the feature that touches one task holds the whole approval.
3. **Answers are folded into the plan before approve.** Specify's readout lists each recorded question by id and title with what its answer would change, and its **Next:** line says to answer them. The human answers with `tiller answer question`, or in chat, where the agent records the answer with `tiller answer question` on the human's instruction (derive-baseline's existing precedent). Specify then writes each answer into the prose it changes (a criterion, `feature.md`, or a `task.md`), re-runs `spec feature`, and its Notes say which answer changed which file. The approved basis then reflects the answers. Leaving answers only on the question was rejected: execute builds from `task.md`, and a plan contradicting an answer recorded elsewhere is the contradiction KoPanda kept hitting.
4. **Execute records a mid-run question and keeps building.** A finding past a departure that needs a human decision is recorded with `tiller add question --blocks <narrowest node>` (the task being built if only it depends on the answer, a later task if only that one does, the feature only when a criterion is in doubt). Execute commits the held task's work to its branch and that state, leaves the task where it stands, and continues with the next legal work in the run; routing already skips held tasks. Departures stay as they are: a wrong fact that only the code settles is built through and noted, not recorded. Semantic merge conflicts still stop on the spot, since they block the aggregate every task shares.
5. **Execute stops only when the run has no legal work left, or at a stop it already makes** (a review handoff, an attestation), whichever comes first. Recording a question never stops a run by itself. At that stop, Notes from this run list every question the run recorded and every open question still holding the run's work, each with its id and title, the node it holds, and what the answer would change. The readout's existing open-question count and `tiller queue` command already carry the mechanical half (#69's counts-only rule), so this needs no CLI change. A count or timer threshold was rejected: either one stops the human while legal work waits.
6. **A mid-run answer resumes or corrects.** An answer that fits the approved plan as written (it picks between options the plan already left open) resumes the held task, with the answer noted in its implementation commit message the way a departure is. An answer that changes approved prose (a criterion, `feature.md`, or a `task.md`) goes through the existing correction table in `tiller guide specify`, the same route an out-of-bounds departure takes today: the agent writes the answer into the prose and the human clears the moved basis with `approve feature --refresh-basis`. The human can answer and refresh in one sitting.
7. **The refusal covers plan gates only.** It applies to `approve feature` from `specced` to `ready` and to `approve task` from `proposed` to `ready` (a task added after the plan gate, for example by intake: its own plan gate, refused when an open question names the task or an ancestor). It does not apply to `approve feature --refresh-basis`, `--review-grain`, or `--assume-question` on a ready or active feature, which are correction or record-only moves; refusing them would block decision 6's own correction while other questions hold other tasks. It does not apply to `approve epic`: an epic's approval only opens its features for specify, and an open question pinned to the epic is inherited, so each feature's plan gate refuses on it. It does not apply to bug, chore, or tweak approval, which intake and capture produce, not specify.
8. **No `--assume-question` escape at the plan gate.** A feature's assumption does not reach its tasks (`TaskQuestionBlockers` ignores it; task start answers "tasks cannot assume away blocking questions"), so a feature approved under an assumption would refuse at every `start`. `--assume-question` also stays record-only and separate by design. A human not ready to decide answers with the call they would make for now ("build it as planned; revisit after launch"), which folds into the plan under decision 3 and leaves a record, or has specify narrow or drop the question.
9. **Every surface stops offering an approve that would refuse.** The queue already hides an approve row that would refuse when copied (#36, #37: "a queue whose commands fail when copied is worse than silence"). The `approve_feature` row is hidden while an open question holds the plan; the question's own `answer_question` row stays. Routing reads the queue (`internal/views/next_enumerate.go`), so a held specced feature routes to the answer, not the approval wait. The orientation text's plan-gate bullet changes to say so, riding generation 54, which gate reuse already bumped in this unreleased release.

## Settled while writing

- **The plan's questions.** At the specced-to-ready approve, the blockers are the union, deduplicated by question id in first-seen order, of `FeatureQuestionBlockers` for the feature (its epic included) and `TaskQuestionBlockers` for each of its tasks not `cancelled`. Only `gen.QuestionOpen` questions count; an answered, resolved, or cancelled one does not. A specced feature carries no assumption basis, so assumptions play no part.
- **Refusal order.** The plan gate's existing arms run first: the retired-epic refusal, then `validateSpec`. The question refusal runs after them, before `approveFeaturePlan` writes anything. A broken spec is reported before a held one, since the spec has to be fixed regardless.
- **Refusal shape.** It reuses `BlockedByQuestionsError` (reason `open_question_blocker`, exit 1, the same data block `start` and `submit` emit). Its human line names `tiller answer question` and never `--assume-question`, which decision 8 rules out at a plan gate; today's transition line ("answer them or pass --assume-question") is right for `start` and wrong here.
- **`approve task --feature <key>` reports per task** (my call, departing from decision 9's "refuses as a whole"). The batch runner already attempts every node and reports a blocked node without stopping the rest, exiting 1 if any was blocked (`applyTransitionBatch`, `internal/cli/batch.go`). A held task comes back blocked with its questions; the unheld ones approve. Making this one refusal atomic would break that convention for one error type, and per-task gives the human what decision 9 meant the by-id escape to give.
- **The `approve_tasks` queue row** is hidden only when every proposed task on the feature is held. While at least one is unheld, the copied command does real work.
- **The console needs no change of its own** (my call, refining decision 9's "greys out"). The console runs no approvals; its approve cards are queue rows with copyable commands (`DecisionCard`, `queueGroups`). Hiding the row removes the card, and the question's own answer card already names what to do.
- **Existing projects.** A project with a specced feature that already has an open question pinned to it sees `approve` refuse after upgrading. That is the intended behavior; nothing migrates.

## Settled while building

- **A mid-run question lands on the branch it is recorded on, and is answered there.** The question ledger is one file, `.tiller/decisions/open-questions.yml`, and execute commits a recorded question to the branch it builds. Integration's queue, the console, and checkouts cut from integration cannot see it until that branch merges, so routing elsewhere neither shows it nor holds the work it names. Execute now pushes the held branch when remote-backed, keeps its worktree, holds a later task or the feature the question names itself for the rest of the run, and names each question's branch and worktree in its run notes. The human answers there with `tiller answer question`, or in chat recorded by the agent on their instruction, and the answer is committed on that branch, the same rule a coarse attest follows on the recorded aggregate branch. Several task branches now edit the ledger, so its mechanical conflicts keep every question.
- **The console's node page needed a change after all** (correcting the console bullet under Settled while writing). When the queue is silent about a node, the node page's fallback (`ui/src/lib/attentionFallback.ts`) recomputed `tiller approve feature` or `tiller approve task`, and `approve_tasks` rows are keyed to the feature, so a proposed task's page always reached it. The fallback no longer offers `approve feature` at all, since the queue's row is hidden exactly when it would refuse, and offers `approve task` only when the page's `relationships.blocked_by_questions` is empty and no retired ancestor holds the task; a held task's page names the question's title, id, and `tiller answer question` instead. `tiller configure`'s **Next** block names the answer the same way.
- **Orientation moved to generation 56** (correcting decision 9's "riding generation 54"). Generation 55 (ranked next) had already shipped locally in v0.21.0 before this branch was cut, and readiness detects stale orientation by generation number alone, so a changed plan-gate bullet under 55 would never refresh a project already on 55.
