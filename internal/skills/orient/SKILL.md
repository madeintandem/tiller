# orient

## Trigger

You begin work in a Tiller repo, or you just finished a step and need to choose the next unrelated work. This is the broadest moment in the set and the only one not tied to a single node's state. When in doubt about what to do, start here. A developer reporting a merge or acceptance decision for already-authorized work instead re-enters `execute` for that work's bounded closeout; it is not permission to start unrelated work.

An explicit request for a UI/UX design brief or prototype handoff for an epic, feature, or task instead loads `tiller guide design-brief` directly. It sits outside the ranked next list, even when the list names a gate or other work. The request already authorizes the read-only export, not specification, approval, or execution. Follow that guide and end with its Markdown deliverable, without orient's readout or next-work handoff. An ordinary next-work request, draft feature, or completed step does not trigger it.

For that export, prefix every Tiller read, including status and guide, with `env GIT_OPTIONAL_LOCKS=0`, and use `git --no-optional-locks` for direct Git inspection. Tiller reads may invoke Git internally; disable optional index writes from the first read, not only after loading the skill.

An explicit request for a code review of one epic, feature, task, bug, chore, or tweak, or a request naming rows of an existing review to log, fix on their branch, drop, or commit, instead loads `tiller guide code-review` directly. It sits outside the ranked next list the same way. The request authorizes only the read-only review or the named disposition, never approval, claiming, or starting. Follow that guide and end with its reply, without orient's readout or next-work handoff. An ordinary next-work request or completed step does not trigger it.

## Reasoning

Apply the developer authorship rule in `.tiller/orientation.md` throughout every seam. The developer owns and is responsible for the work. Never identify yourself, your agent, model, provider, or harness as an author or contributor in code, comments, docs, commits, PRs, issues, reviews, reports, or replies. No generated-by notices, agent signatures, badges, footers, or agent co-author trailers. Describe the work and observed verification, not the tool that produced it.

Read the lay of the land, then relay the ranked list to the developer and end the reply. You are not doing the work at the seam in this reply, and you do not cross into it either: the crossing into the seam skill comes after the developer's next message, which redirects you or lets the top agent move start.

That stop is the briefing before a seam is authorized. Once the developer has instructed execute, continue related checks, evidence commits even on check exit `1`, rubric preparation, draft review publication, and, after human acceptance, formal submission and state publication/readback without a second go. A reported final merge continues the same work on integration through applicable feature acceptance, ordinary sync, state commits, push, and readback, without a new state-only PR. Before an acceptance-only handoff execute verifies a matching draft or committed offline review surface and names the exact human decision; pure orient never opens that review. Explicit no-publish or earlier-stop instructions control. No agent attests, asserts a fast-forward crossing, or performs the final integration merge. Intermediate task-to-aggregate assembly is agent-authorized.

A few reads tell you where things stand. `tiller status` with no node gives the project summary: the project, its registered contributors, and how many nodes of each noun exist. `tiller queue` gives the current attention entries from the Queue projection; use `--kind <queue-kind>` and `--noun <noun>` only to drill into the count summaries the readout names. `tiller ls bugs`, `tiller ls chores`, and `tiller ls tweaks` show the three standing shelves in soft order. The readout always carries the exact standing line `queue: N bugs, M chores, K tweaks ready`, with the actual counts and singular nouns when a count is one. `tiller status <noun> <node>` gives one node's state, the `next` moves the lifecycle allows from there, its recorded gates, and, when a spec or contract has been edited out from under approved work, an `active_basis` line naming the file and the command that re-pins it. That one-node oracle is the only surface that reports basis drift; the project summary does not, so when a gate refuses on a basis you did not expect to have moved, ask the node. `tiller ls features --contributor <you> --status active` shows active features you have contributed to, `tiller ls tasks --status check` finds checked work still awaiting submission, and `tiller ls tasks --status in_review` shows task submissions whose resolved review may still need publication.

For discovery, use `tiller search <keyword>` for prose and `tiller query --from <address> --follow <directions> --json` for recorded relationships; `query --help` lists the complete forward/inverse catalog. A work ID with `--follow mentioned_by` finds document citations, including labeled generated mentions. A `path:<repo-relative-path>` start with `--follow covered_by` finds exact or enclosing recorded scopes, not verified implementation coverage. Repeat `--from` for several starts; follow names are a union at every hop, depth defaults to one, and exact kind/status/owner filters select after traversal without hiding bridges.

Read query diagnostics and `complete` before calling discovery exhaustive. Missing eval/history input or ambiguous historical identity is incomplete; unsafe corpus or unstable-generation reads fail. Unknown references do not become current nodes, and opening a current file does not retrieve pinned historical bytes. Question `blocks` edges are recorded targets, not effective inherited holds or assumption waivers: keep status/readout as the authority for legal work. These reads require no identity and write no files, events, or persistent cache; they never run bindings or refresh guidance.

From that picture the dispatch is a ranked list. Run `tiller next` (or read the readout's **Next:**). Relay the list as written. If any human move ranks above the top agent move, name it first. Then start the top agent move unless the developer redirects. Start it in your next turn, once the developer's reply does not redirect. You may say you would take a different item first and why; never rewrite the list. A ranked move is a suggestion, not authorization.

The list holds at most five legal moves for this checkout, human decisions included, one row per node. Each row leads with its actor, `You` or `Agent`, then the action, the reason, and the exact command, or the branch to continue on. Tiller ranks the moves by a fixed rule, in five tiers. Unblock nearby comes first: human decisions that hold work in your current feature, plus any question overdue or due within two days wherever it sits. Continue is your own unfinished work, and your top Continue move is always kept in the five. Nearby is the rest of the current feature, then its epic. Recently touched is the features and epics you acted on within the last fourteen days, most recent day first. Everything else follows in plan order. The current feature is the feature touched by your most recent deliberate act that names one: a claim, start, submit, check, spec, approval, answer, attest, link, reassign, or release. Acts on an epic alone and amendment steps never set it, and adding work only touches its parent for recency, so a decomposition never sets it. `tiller next --all` lists every legal move and `--contributor` ranks for someone else. With no identity, `tiller next` and bare `tiller guide` head the list as not personalized (the readout's **Next:** has no heading), the personal tiers are skipped, and plan order ranks the rest, though a question overdue or due within two days still ranks first; `tiller join` fixes that. When nothing is legal it says `Caught up`.

Bare `tiller guide` prints the same list, then names the skill for the highest-ranked agent move, since the top row is often the human's. Your pick and the CLI's cannot disagree for every move the list computes from the recorded tree. The `mend-drift` seam is this skill's own addition: knowing it applies takes an actual `tiller drift` run, which the list never makes on its own, so neither `tiller next` nor `tiller guide` suggests it. The `amend` seam is another such addition, for a kindred reason: a reshape is named by the developer's judgment, or by reading a drift cascade whole, never by a field in the tree. `capture` also sits outside the list: when an investigation or developer description identifies a concrete bug, chore, or tweak, the operator initiates capture rather than reaching it through a ranked move. The amendment wait below is not an addition of that kind: the list does name it, because a proposed amendment is recorded state like any other.

Ownership gates execution, not judgment. Claim the task with `tiller claim task <key>` before starting, submitting, or resuming it; claim bugs, chores, and tweaks individually after the human selects shelf work. A first successful start permanently fixes that unit's owner and atomically activates a ready parent feature. Before start only, release or human-directed reassignment can change the reservation; all terminal ownership is immutable. Never take another reservation merely by changing `--contributor`: `claim --from <holder>` needs an explicit human handoff. The judgment verbs remain open to every registered contributor, with unchanged delegation boundaries: `approve` and `resolve` require explicit human instruction naming the node and target; `cancel`, `attest`, `sync --accept-fast-forward`, and final merge remain human-only. A feature-only assumption uses `tiller approve feature <ref> --assume-question <Q-id> --reason <text>` without moving lifecycle or silently granting the task an assumption.

Features and epics display Contributors, the distinct owners of descendant tasks that have started, including done or cancelled tasks. Reservations, review actors, creators, and attached shelf owners do not count. Personal work means unfinished task/bug/chore/tweak assignments, including proposed, blocked, checked, and in-review states, not all work beneath a past contribution. `tiller ls features --contributor <id>` finds history; `tiller ls tasks --owner <id>` finds scalar assignments.

Started unfinished work changes hands only through `tiller transfer task|bug|chore|tweak <ref> --to <contributor-id> --reason <text>`, explicitly authorized by a human naming the work and recipient. It preserves the original and creates a same-scope ready replacement, not an ownership override. Explain refused scope drift, terminal/same-owner transfers, or started dependents without inventing commands; use execute's continuation protocol. Closing an old PR, starting the replacement, updating an aggregate, and rechecking acceptance remain separate Git/host work.

Treat review-grain configuration as a gate decision and name its safe timing in the briefing. Finish and sync submitted work before changing a review grain that would affect it; an affected feature review, an affected task in `in_progress`, `check`, or `in_review`, or an affected branch when entering or leaving epic grain makes `configure` refuse. Do not propose a state-file edit as recovery. If `configure project` reports an unsupported `execution` shape, rewrite the human-owned manifest setting as block-form YAML and rerun the command.

Different owners may execute tasks in one feature or epic review. Any registered developer may perform authorized aggregate assembly, checks, and submission; no coordinator claim exists. Coordinate one updater at a time through the team and Git. An overridden feature finishes its own task- or feature-grain PR and reaches `done` before the epic PR opens. A coarse finish line still checks retired ancestors, active basis, questions, reviewed assumptions, gates, readiness, and review identity.

Every task owns its recorded working branch, even when it rides a coarse review. Feature/epic branches are aggregates, not task workbenches. Authorized execute creates task and aggregate branches, ordinary-merges submitted task tips and their state into the aggregate, handles mechanical conflicts, and maintains the same aggregate PR. Independent tasks start from integration; coarse dependents may start from the assembled aggregate. Requested changes resume the task's own branch, then reassemble and rerun affected gates. Do not hand routine branch assembly to the developer. Only the final integration merge, acceptance, or a semantic conflict requiring judgment is a human stop; intermediate assembly is not a done crossing.

Maintenance is separate from choosing lifecycle work. On an explicit maintenance request, `tiller upgrade` updates the installed binary and the current checkout's supported schema and generated artifacts. `tiller upgrade --project-only` repairs this checkout with the running binary, offline and without Homebrew; use it for stale generated guidance or a second checkout after a machine update. `--binary-only` deliberately excludes the project; it cannot combine with project-only, and project-only cannot select `--version`. Join remains onboarding or deliberate identity selection, never the routine refresh remedy. Missing identity still calls for `tiller join --as <you>` after human registration. Artifact-only refresh needs no identity; a real migration resolves a registered actor through `--contributor`, `TILLER_CONTRIBUTOR`, then local identity. The schema-9 migration preserves the selected identity while renaming its field.

Verified Homebrew installations keep brew as their installation owner: upgrade delegates only the matching Tiller package, suppressing implicit dependent upgrades and cleanup, while genuine dependencies and metadata refresh remain brew's responsibility. Exact version pins refuse there. Never overwrite Cellar/Caskroom files or bypass private-download authentication after a failure. Brew may already have changed the machine before the target's project compatibility is established; report that boundary rather than promising a global rollback.

For schema-6 adoption, inspect with `tiller migrate --dry-run --json`, save the whole report or `data.ownership_review` outside source state, and have the human fill every initially empty `confirmed_owner` for started unfinished task/bug/chore/tweak work, leaving all other snapshot fields unchanged. Apply once with `tiller migrate --ownership-review <file>` or `tiller upgrade --project-only --ownership-review <file>`; stale or incomplete review refuses. Schema-5 work can remain active with open reviews and unchanged branches/evidence. Only crossing schemas 2 to 4 into schema 5 needs old shared-branch work drained using a verified compatible binary, including human final merges and sync. Keep its directory on PATH for that temporary drain session, then leave the session; never mutate migrated state with an older binary.

Schema 8 adds Tweaks. The 7-to-8 migration is manifest-only: existing Bug and Chore records remain unchanged, and no work drain is required. Older binaries refuse schema 8; upgrade every participant before resuming mutations.

Schema 9 renames the project roster to `contributors:` and checkout identity to `contributor:`. Use `tiller add contributor <id> --name "<name>"`, `tiller remove contributor <id>`, and `--contributor` or `TILLER_CONTRIBUTOR` for acting identity. Task, Bug, Chore, and Tweak claims remain `owner`; ownership filters remain `--owner`. The 8-to-9 migration preserves IDs, claims, active work, and history without a work drain or ownership review. Legacy command, flag, and environment names are not aliases.

Adoption is coordinated Git work, not independent migrations in stale clones. Retain a compatible binary and committed recovery baseline, pause state mutations, reconcile owners/state on designated integration, review and apply one migration in one checkout, then commit/publish it. Upgrade every participant and merge migrated state into each continuing work branch without discarding its task records. Refresh each checkout, restart consoles, reload agent instructions, and check schema, identity, task owner, branch, and legal next action before resuming. Adoption is not authorization or an evidence waiver. A schema fence does not stop stale unmigrated clones; after adoption preserve new work during recovery rather than blindly restoring old files.

Read phase outcomes even on failure: a binary replacement or source migration can have completed before refresh fails. Preserve completed state and review the reported diff; retry `tiller upgrade --project-only` only after the named cause is repaired. `mutation_recovery_needed` requires transaction recovery first, not cache/journal deletion. Unknown durability is not proof of no writes. Other branches, worktrees, and projects are untouched; teammates incorporate the reviewed migration and maintain their own checkouts. Restart existing serve processes and reload harness instructions as needed. An already-running older binary cannot gain this upgrade logic during replacement: retain a compatible old executable before the first new install and run the new binary's project-only command afterward.

Workflow advice is separate from the node's lifecycle `next` moves. Inspect authored contract bindings and the current applicable required gates alongside recorded results: missing, unconfigured, failed, or stale machine work calls for checks/repair; an ungraded or stale rubric calls for grading and recording; only complete machine/rubric work can leave a human-only acceptance wait. Unreadable or invalid contracts are uncertainty, never inferred acceptance. Optional criteria do not become blockers. At epic grain name both the epic review and the particular feature contract needing work, never an epic eval. A task-grain feature with all live tasks done needs acceptance and ordinary sync before clean closeout. Already-done work with unresolved acceptance or historical violations stays done and visible, not a resume target.

The ranked list is pure: it cannot verify drafts, host state, or pushes. Say "formal submission not recorded," not "no PR exists." A riding task ref is not feature acceptance or formal coarse submission. Execute supplies verified host facts in run notes before its handoff. Recommendation order is not full mutation-guard parity: respect named basis, question, dependency, ownership, and retired-node diagnostics rather than advertise a known-refusing command as clean work.

These are the moves the list can hold and the seam each one leads to:

- The repo is not a Tiller project yet (no `.tiller/`, or `tiller init` has not run), this is the onboarding entry. Scaffold with `tiller init --key <key> --kind <archetype> --name "<project name>"`, adding `--design <dir>` to import a design folder in the same move; the three flags are required and init refuses without them. Registering a person and selecting your identity are separate deliberate acts: a human runs `tiller add contributor <you> --name "<full name>"` (an agent only on explicit instruction naming both), then `tiller join --as <you>` selects that registered identity. Without them mutations lack an acting contributor and readiness reports an empty roster. Tiller never runs your agent. Init runs now; name the applicable first seam below and stop for the developer's go. Greenfield prepares design inputs for decompose. Brownfield and legacy-migration first derive or reconcile a baseline; an import alone does not confirm one.
- `project.kind` is `brownfield` or `legacy-migration` and `.tiller/design/baseline.yml` has no confirmed doc, the seam is `derive-baseline`, even when epics or work already exist. Read the ledger and pending prose before proposing new writing. Existing unconfirmed docs may already be a complete committed proposal: inspect/reconcile them or hand them back for human review with `tiller approve design <doc>...`, never blindly regenerate duplicates. The baseline review is not a work-node queue entry. One confirmed doc releases this startup move; remaining pending docs are not a global gate. Contributors, legacy reference declarations, root modes, and other readiness gaps remain independent.
- The tree already has epics, and inputs exist under `.tiller/design/` that it does not yet reflect: the seam is `decompose`, after the existing-code baseline move above.
- You hold a task in `check`, `ready`, or `in_progress` and no operative direct or inherited question blocks it: the seam is `execute`, and the list files it under Continue. Re-enter checked work on its recorded branch without start/resume, and preserve dependency and soft order. Shelf work you hold in those states is the same move. An unclaimed shelf node is not suggested, and live carried work waits on its carrier. Ownership is per unit, never inherited from a feature. Assignment visibility includes non-executable proposed/blocked and in-review work without advertising it as ready.
- A task held by an operative open question is not a move; the holding question is, as a human answer. Name `tiller answer question <Q-id> --answer "..."` as the developer's move. Answering one question may leave other blockers.
- A proposed amendment awaits the human's approval: that is `tiller approve amendment`, the human's move, not a seam. Name it and stop. `tiller ls amendments --status proposed` names what is open, and several can be proposed at once, each its own row.
- Shared feature/epic closeout appears once per reviewed unit. A coarse finish line derives assembly, checks, rubric work, human acceptance, and submission from feature contracts; task-grain features with every live task done need feature acceptance and ordinary sync on integration. Do not assign this work to the last finisher or historical contributors. A ranked closeout move offers related closeout but does not authorize it. Pure reads cannot claim a draft exists; authorized execute prepares the real review surface before handing off acceptance.
- An unclaimed eligible `ready` task under an approved ready or active feature: the seam is `execute`, naming `tiller claim task <key>`. Preserve epic/feature dependencies, approved bases, operative questions, and task order. Approval itself neither claims nor starts a task; the suggestion is not authorization.
- A feature sits `specced` awaiting its plan gate with no open question holding its plan: that is `tiller approve feature`, the human's move, not a seam. Name it and stop. A plan held by an open question (on the feature, its epic, or any live task under it) is not that move; the question is, as a human answer. Name `tiller answer question <Q-id> --answer "..."`, after which specify folds the answer into the plan before the approve. A question that needs no decision leaves by `tiller cancel question <Q-id> --reason "..."`; cancel and `tiller unlink question <Q-id> --blocks <node>` are human moves, so name the exact command rather than run it unless the human told you to.
- An epic sits `draft` with live features under it, awaiting its decomposition gate: that is `tiller approve epic <key>`, the human's move, not a seam. Several epics list in recorded soft order. `tiller spec feature` stays legal on any draft the developer names; the gate shapes only the suggestion.
- The frontier is the project's live draft features whose feature and epic dependencies are settled (`done` or `cancelled`), in dependency-plus-soft order: the seam is `specify`. Features and epics have no owner, so never present the frontier as one person's reserved work. Explicitly named drafts remain legal to specify even when the list does not show them. A draft waiting on unfinished work is no move and never a row. When every draft waits, the tree is still not empty: dependency diagnostics (Home, `tiller check readiness`) and the caught-up hint explain the held work.
- A task, bug, chore, or tweak sits in `in_review` because its PR review requested changes, the seam is `execute`, which re-enters through `resume` and reuses the existing open PR. An old PR number on resumed or checked work does not mean the changes were resubmitted. Nothing in the tree records that a review asked for changes, because that lives on the PR, so this arm is read off the conversation rather than off state, as the `amend` arm below is.
- `tiller drift` reports a candidate and nothing in the list already claimed the moment, the seam is `mend-drift`.
- The change in front of you reshapes the plan rather than extends it, whether the developer says so or a `tiller drift` run reports one upstream change cascading across a dozen nodes, and the seam is `amend`. Nothing in state names this one, so it is reached by judgment: say what you think it is and let the developer confirm before anything is staged.
- A node sits cleanly in `in_review` only waiting on a merge: a human wait, not a seam. A live carried shelf node waits on its carrier instead. At coarse grain a riding task's `in_review` alone proves neither acceptance nor formal review; inspect the resolved feature or epic. Outstanding acceptance may still be a human decision, while absent machine evidence or an ungraded rubric remains agent work. When formal review is recorded, name only that recorded identity and do not infer its current host state. If an authorized run still owes ordinary state publication, finish it rather than hand the second push to the human.
- No epics are recorded and no move above applies: decompose is due only when a to-be design doc exists, a file under `.tiller/design/` (dotfiles excepted) that `baseline.yml` neither registers as an as-is doc nor cites as a source, and then the seam is `decompose`. With none, no work is planned yet, a human wait: name the open-question count and the ways work enters (intake, capture, or a to-be design) and stop, without proposing epics from as-is docs or old specs. On a tree with no epics, owned shelf work in `check`, `ready`, or `in_progress`, a proposed amendment, and a shelf merge wait still list; unclaimed shelf work never does.
- Nothing is on the frontier or in the executable work loop: the list prints `Caught up`, which is not necessarily empty. No eligible unclaimed ready task remains. A diagnostic can still count unfinished unclaimed tasks that are proposed, held, or otherwise ineligible, explaining the first dependency-ranked task without a claim/start command. This differs from the eligible ready-task pool. An eligible unclaimed task is a claim move, not caught-up; a held reservation, past contribution, or draft feature is not a claimable task.

The list needs no side notes. What the old notes described is now a row of its own: the holding question, your own in-flight branch, the neighbouring feature, and the next eligible task each rank as moves. Do not add a note that steers toward or away from a ranked row beyond saying you would take another row first and why.

The lifecycle is the queue: `draft` is the backlog, `specced` and `ready` are on deck, `active` is in progress, and only the human's go pulls a feature forward. Plan the known scope as bounded product and platform increments, not permanent subsystem buckets, then specify each feature just in time. Related capabilities can recur in later increments. Record true prerequisites as `depends_on`, preferred sibling sequence with `tiller order`, and execution responsibility per task. Soft order never gates execution. There is no layer of planning between the tree and the work.

A move that is not legal does not appear, so an ineligible preferred node never blocks a legal alternative. Inside a tier, moves sort by kind in a fixed order first: the baseline, your own continuing work, amendment review, closeout, claiming, resolving a blocker, plan approval, epic approval, specify, merges, answers, attests, triage, then decompose. Within a kind, plan order decides: epic order, feature order within an epic, and task order within a feature. Tier 1 sorts by due date first, overdue first. A task's local ordinal is not global priority over unrelated features. Completed prerequisite depth does not outrank a live preference; historical tree rendering and stored dependency edges remain unchanged.

One feature just in time remains specify's default. An explicit instruction naming exactly several draft features, or every draft feature in one named epic, creates a bounded batch that overrides the list's pacing only for that set. Follow rendered soft order. Complete the full specification, contract, and tasks for one feature, run `tiller spec feature`, and make its separate feature-only commit before continuing. Add no unnamed siblings, never approve, and finish the batch with one final `tiller readout specify`.

The ranked list is guidance, not command authority. An explicit human instruction naming nodes overrides the list's order for exactly those nodes. When recorded state leaves a gate or merge outstanding, say `the ranked list suggests waiting`. Describe a wait as a Tiller requirement only when a command actually refused. Only exit `1` is Tiller refusing with a business answer; exit `2` or `3` means correct the call or environment.

## Correction routing

Approval does not freeze cosmetic titles, epic narrative, additive child work, soft order, or same-scope prose on a non-terminal feature or task after human review. Accepted basis, terminal history, and active structural work still have teeth. Classify explicit human feedback before choosing a seam:

For structural feedback, first load the installed `tiller guide amend` and its read-only feasibility preflight, along with `tiller rename --help` and `tiller amend --help`. Before placement negotiation, inspect affected node/descendant states and execution history, branches/reviews, both parents, dependencies, effective question holds, and inherited review settings. Explain recommended outcome, installed capability, and smallest safe alternative separately; ask for product decisions, not facts available in the repository. Use the same correction rules as `.tiller/orientation.md`, not a trial mutation or an invented dry-run.

- **Unapproved proposal:** Re-enter `decompose`, apply its draft correction, and return to the same epic approval gate, not `amend`.
- **Pending baseline proposal:** Re-enter `derive-baseline`, correct the named docs and relationships in place, reconcile current described code, commit, and return to the named-doc human confirmation gate. Do not make duplicate docs or treat the correction as a work-node amendment.
- **Pre-work feature plan:** Re-enter `specify` and return to the same feature approval gate. If a ready plan's approval should replay, use `return`, revise it, and reapprove before work starts.
- **Accepted lightweight change:** Follow `specify`'s mapped direct command for a title or soft order, its prose edit and `active_basis` refresh for same-scope non-terminal feature or task prose (a wrong fact found while executing a task is an execute departure recorded with the work, not an edit), or its direct additive task path with that task's own task approval. Do not invent an amendment for work that only extends the accepted plan.
- **Unchanged feature relocation or local-key correction:** Direct `rename --key` requires a draft, task-free feature; changing parents additionally requires draft source and destination epics. Otherwise use amend's reviewed `move-feature` for eligible draft, specced, or ready features whose descendants have never started, preserving identity and stopping at amendment approval. Name a started descendant and its history as the refusal; do not manufacture a replacement or edit state around the restriction.
- **Genuine structural reshape:** Use `amend` for cancellation, supersession, or replacement in the requested scope. It has no link, unlink, or order operation; revise re-pins prose, not dependencies. An in-place hard-edge edit on unchanged started work remains unsupported, and replacement must not be manufactured to evade that lock. Fresh unstarted tasks can receive legal prerequisites under an active feature. Preserve terminal feature/task prose and completed descendants; same-outcome additions can continue under done parents, with sync reopening rollups, while distinct outcomes get new increments. Cancelled or archived ancestors are not continuation targets. Propose wider replanning for developer direction.

Bounded epic features may interleave. A projected epic ordering cycle is a nonblocking advisory, not an execution deadlock. Explain the implicated features and recorded edges; actual prerequisites, including explicit epic dependencies and mixed feature/epic completion obligations, still block. Do not tell the developer to break valid prerequisites simply to make grouped rendering sort cleanly.

An explicit human correction that maps to a class authorizes the selected action and is already the developer's go for that action, except when the mapped command is `cancel`. For any cancellation, hand the exact `cancel` command to the human rather than run it. Do not ask which mutation path to use when the class answers. Run other machine-state changes through `tiller`, edit only human-owned Markdown, never hand-edit machine state, read the result back, commit it, rerun the current readout with `--since <sha>` naming the commit the last block you reported, and return to the applicable approval, refresh, reapproval, task-approval, or amendment gate. A seam exit keeps the full readout; a correction inside a gate gets that lighter block.

## Recovery protocol

Skills correct themselves from the CLI's exit codes without a human. A `1` is a business answer to reason about, usually a red gate or an illegal transition; fix the work and try again, do not escalate. A `2` or a `3` is a mistake in how the command was called or in the environment; fix the call. When you are unsure what is legal from here, `tiller status <noun> <node>` names the next moves with nothing executed. This protocol is inherited by every skill, so the others only point back to it.

For `design-brief`, recovery is limited to corrected reads. Report missing sources, drift, and unavailable instructions as limitations; do not repair sources, refresh instructions, record questions, or enter another skill to fill the gaps.

For a `code-review` review, recovery is limited to corrected reads. A disposition records through `tiller` commands and recovers by the ordinary protocol above.

## External references

In authored prose, link the first mention of an external library, framework, service, standard, tool, or other reference to its canonical home or the specific page relevant to the claim, using an HTTPS Markdown link. Use a URL only when it is present in the inputs or was fetched live in this session and returned a page identifying the intended reference. A failed fetch or a search snippet is not verification. Never guess a URL, even for a familiar name or a seemingly obvious homepage or domain. If neither source is available, write the name as plain text. This house rule applies across skills and hand-offs; it does not authorize fetching unrelated sources or changing accepted historical prose.

## Node references

When you talk to the human about a node, name it by its key path with the id in parentheses: `form-engine/certification-form-loading (F-79dh3q)`. A task carries its own three-segment key path, `form-engine/certification-form-loading/schema-transcription (T-k3p9w6)`. A question is never keyed; name it by its id plus its short title, and use the full statement when the question itself is the subject. In command position an existing node takes either form: a bare id is always valid, and a keyed noun also takes its key path. The `add` verbs are the exception, because they name a node that does not exist yet by the key path it will have, so every segment there must be a key: `tiller add feature <epic-key>/<feature-key>` and `tiller add task <epic-key>/<feature-key>/<task-key>` refuse a parent addressed by id with exit `2`. A question is id-only in command position, since it is never keyed. This convention is inherited by every skill, and each one repeats the output half at its own reporting moment, because that is where a bare id actually leaks and a bare id is exactly the thing the developer cannot read without looking it up.

Bugs are defects. Chores are housekeeping without code side effects, as guidance rather than validation. Tweaks are minor adjustments that may change code; Tasks are substantive planned work. Capture forward adjustments with a new Tweak contract and human triage, never by reopening done work.

## Choreography

Reads, plus the one scaffold. This is the skill whose output is a decision rather than a state change. On a bare repo `tiller init` is orient's to run; the stop lands after it, before the applicable first seam: derive-baseline for an unconfirmed existing-code project, decompose when a to-be design doc exists, and otherwise the no-work-planned end state. A delegated `approve` runs only on an explicit human instruction naming the nodes or design docs, after the stop, never as the next line of an orient.

```
# cold start only, on a repo with no .tiller/: the scaffold, then the stop.
# init is the one command this dispatch runs for you; add contributor and join are
# shown for reference; the developer runs those, on a human's explicit go.
tiller init --key <key> --kind <archetype> --name "<project name>"   # add --design <dir> to import inputs
tiller add contributor <you> --name "<full name>"       # a human registers you; without it join and every mutation refuse
tiller join --as <you>                                 # selects the identity add contributor just registered; without it add/start/check exit 3

# every run: the reads the dispatch is made from
tiller status                                          # the project summary: the project, its contributors, its counts
tiller queue                                           # exact current attention entries; add --kind or --noun to drill down
tiller ls bugs                                        # the standing bug shelf in its soft order
tiller ls chores                                      # the standing chore shelf in its soft order
tiller ls tweaks                                      # the standing tweak shelf in its soft order
tiller status feature form-engine/certification-form-loading    # one node's state, its next moves, its gates, any active_basis drift
tiller ls tasks --owner robin                            # your scalar task assignments
tiller ls features --contributor robin                    # started-task contribution history
tiller ls tasks --status check                         # checked work still awaiting submission
tiller ls tasks --status in_review                     # current task submissions; coarse refs may still need the resolved review
tiller drift                                           # are there candidates waiting; a marker names the seam mend-drift
tiller ls amendments --status proposed                 # is a staged reshape waiting on the human's approve
# optional relationship discovery; these do not choose or authorize work
tiller query --from F-79dh3q --follow mentioned_by --json
tiller query --from path:app/models/calc --follow covered_by --json
# On an existing-code startup, also inspect the baseline ledger and its docs.
# If a proposal already awaits confirmation, inspect it rather than derive again.
tiller readout orient                                  # the picture, rendered as the one block every harness renders the same way
```

Note: `tiller ls plans` does not exist in this build; do not call it. `ls` takes epics, features, tasks, bugs, chores, tweaks, questions, and amendments.

## Readout

orient lays nothing down, so its block is not a report of work done, it is the picture itself: the same
survey the Reasoning section above just walked, rendered the one way every harness renders it. Run
`tiller readout orient` and reproduce its block verbatim as the last thing in your reply.

The block carries one singular `Needs attention` list. It is counts-only: each bullet states an exact
Queue count and an inline `tiller queue` drill-down. Do not expand it into concrete node rows, question
rows, gates, criteria, or mutation commands. The queue command is the one place to enumerate a count.
Do not narrate the picture again in prose around the block or summarize the ranked list in your own words.
Baseline docs awaiting confirmation have their own review presentation, not a fabricated `approve_design` queue kind. Keep the rendered baseline review and human next action intact; an empty work-node queue does not mean those docs need no human.
The block closes the reply and ends on its **Next:** ranked list, the one place the developer looks to learn what happens next. Reproduce the list as written; your own pick, if it differs, goes in the notes ahead of the block.

Before the block, add a short **Notes from this run** list for what it cannot know: context from earlier
in this conversation that changes the read, a correction the developer should make to the picture, or a
question worth recording rather than assuming an answer to. Keep it to facts about this run. In the
notes and in everything else you write to the developer, name every epic, feature, and task the way the
block itself does, key path with the id in parentheses, never a bare id: an id alone sends the developer
off to look up what it points at. After the block, stop;
the developer's next message is the redirect or the go, same as always.

## Hand-off

Up to the developer, always. Surface the picture and the ranked list, naming any human move that ranks above the top agent move, then end the reply. Their next message redirects you or lets the top agent move start, through its seam (`derive-baseline`, `decompose`, `specify`, `execute`, `mend-drift`, or `amend`). The briefing is where they correct your understanding and add project context; conventions worth keeping belong in `AGENTS.md`. A deferred briefing item becomes a recorded question (`tiller add question "<statement>" --title "<short title>"`, with `--blocks` naming held work), not chat history. Some moves are human gates: pending baseline confirmation, a staged amendment, draft epic, feature plan, open question, or final merge wait. Surface the applicable gate and stop. Run `approve` only on explicit human instruction naming nodes or docs; baseline derivation never authorizes its own confirmation. `attest`, `sync --accept-fast-forward`, and final integration merge remain the human's keyboard, not ordinary aggregate assembly.
